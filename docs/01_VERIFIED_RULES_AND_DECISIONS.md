## 1. 已确定的开发与参赛决定

- 保持 Track 1。产品中心是 HSKSwap 上可检查的 AI 自主交易闭环，并支持自然语言查询和修改授权范围内的策略。

- 按线上 Demo 准备。官方允许线上展示，但能够在孟买现场展示的团队享有入选优先；这会影响竞争条件，不能承诺线上与线下选择机会相同。
- 在规则正文较早截止前完成正式提交与主网部署。按下表的内部节点提前收敛范围，避免将时间消耗在非必需组件上。
- 未公布评分权重、报名表单附加字段或领奖条件时，标记为待确认；先继续不依赖这些条件的编码、测试和材料准备。

## 5. 内部验收建议：与官方硬要求分开

下面的目标为了提高评委核验效率，由本项目自行采用。未经进一步证据，不得在 README 中加上“官方强制”字样。

| 内部目标 | 为什么采用 | 实施与真实性要求 |
|---|---|---|
| 可复现仓库与最终 SHA | 评委能对齐演示、源码和部署 | 记录最终提交、构建配置、部署参数、许可证及运行说明 |
| 浏览器合约源码验证 | 降低评委检查部署的成本 | 尽量完成；若浏览器验证服务失败，应报告失败及替代字节码/构建证据，不能伪称已验证 |
| 至少一条可复核的主网成交闭环 | 证明核心功能实际运行 | 数量不是已公布硬标准；真实回执与余额变化优先，不能为凑数量强迫策略交易 |
| 一次越权意图被拒绝的演示 | 清楚说明控制边界 | 标明发生在本地、fork、主网 eth_call 或真实失败交易；四者不得混称 |
| 一次自然语言策略变更后行为变化 | 证明用户控制贯穿执行 | 展示旧值、新值、用户批准、链上/运行状态及后续决定 |
| 盈亏报告与不交易决定 | 交易有效性不能只看成功哈希 | 区分实盘、历史回放、合成样本；扣费计算、数据期间、基准和样本局限齐全 |
| 约三分钟的核心演示草稿 | 让评委快速理解问题与成果 | 时长只是初稿目标，按官方最终安排修改；备用录像必须标注录像 |
| 主网证据包与提交状态记录 | 避免版本错配和漏交 | Draft、Submitted、Selected、Winner 各自记录，不得跨状态宣称 |

主网合约部署是官方硬要求；可复核的交易、风控、自然语言功能是证明赛道契合度的关键证据。提高获奖竞争力依赖完整度、实际价值及演示表现，不能用组件数量、测试条数或提交人数计算可靠获奖概率。当前官方 Builds 页未公开可查看的项目列表 [R5]。
